## 1. 배경과 목적

### 1.1 사업 맥락

사업계획서 [5]-다. 플랫폼 트랙에 명시된 요구사항:

> 브이로그 공동제작 학습자(10인) 본인 계정으로 "내 책상" 페이지 운영 가능, **사업 종료 후 자발적 콘텐츠 업로드 지원**

또한 [5]-나. 콘텐츠 트랙의 스크립트 **B형(기록형)** 은 "플랫폼 「나의 한국어 책상」에 하루하루 공부한 내용 기록"을 전제하며, [5]-라. 이벤트 트랙의 서울 행사 초청자 선발 평가에서 **"플랫폼 기여 20% — 「나의 한국어 책상」 페이지 작성 충실도·꾸준함"** 이 정량 평가 항목으로 사용된다.

즉 이 페이지는 부가 기능이 아니라 **콘텐츠 트랙과 이벤트 트랙이 물려 있는 사업 인프라**이며, 8월 촬영·기록 단계 시작 시점에 반드시 가동되어야 한다.

### 1.2 목적

1. 최대 10인의 브이로그 공동제작자(공동제작 학습자 8인 + 현지 크리에이터 파트너 2인)가 **본인 계정으로** 한국어 학습 여정을 블로그 형태로 기록한다.
2. 사이트 방문자 누구나 로그인 없이 그 기록을 **읽을 수 있다.**
3. 사업 종료(2026-10) 이후에도 10인이 **계속 자율적으로** 업로드할 수 있도록 계정·데이터·비용 구조를 설계한다.

### 1.3 비목표 (Non-goals)

- 일반 방문자의 글쓰기·회원가입 (Phase 3 이후 별도 판단)
- 댓글 시스템 (Phase 3)
- 브이로그 영상 자체의 호스팅·인코딩 (유튜브 채널이 담당)
- 기존 앱 리뷰 기능과의 계정 통합 (기존 리뷰는 localStorage 익명 방식 유지)

## 3. 핵심 설계 결정 — 로그인을 어떻게 보여줄 것인가

### 3.1 문제 정의

> "로그인 버튼을 그 10명이 접속할 때만 뜨게 해야 할지, 근데 그건 또 너무 깔끔하지 못한 것 같고, 단순 방문 목적인 사람들은 '접근이 불가한 페이지가 있다'는 사실을 마음에 들어 하지 않을 것 같다."

이 고민의 핵심은 **접근 제한 자체**가 아니라 **접근 제한이 어떻게 읽히는가**이다. 같은 제한도 "너는 자격이 없다"로 읽히면 배제이고, "이 공간은 원래 이런 곳이다"로 읽히면 큐레이션이다.

### 3.2 결정 — 초대코드 가입 + 로그인 진입점 상시 노출

**공개 읽기 + 초대코드 기반 가입 + 로그인 링크는 항상 보이되, 문구로 성격을 설명한다.**

구체적으로:

1. **로그인 버튼은 숨기지 않는다.** `/desk` 페이지 헤더 우측에 조용한 텍스트 링크로 상시 노출한다.
   - 로그아웃 상태: `책상 주인이신가요? · Are you a desk owner?`
   - 로그인 상태: `내 책상 관리 · My desk` + 아바타
2. **클릭하면 로그인 모달이 뜨고, 모달 상단에 성격을 먼저 설명한다.** (확정 문안)

   > 「나의 한국어 책상」은 2026 국민공공외교 사업의 일환으로 만들어진 기록 공간으로, 인도네시아와 필리핀의 한국어 학습자 **{N}인**이 자신의 학습 여정을 직접 기록하는 곳입니다. 누구나 이들의 학습 여정을 읽어보고 함께할 수 있습니다.
   >
   > *Korean Desks of the World is an archive created as part of the 2026 Korean Public Diplomacy Project, where **{N}** Korean-language learners in Indonesia and the Philippines record their own learning journeys. Anyone is welcome to read along and join them.*

   - `{N}` 은 **하드코딩하지 않는다.** 활성 저자 수(`profiles where role='author' and is_active`)를 조회해 렌더하거나, 운영자 대시보드에서 설정 가능한 값으로 둔다. 참여 인원이 확정되기 전에는 숫자를 생략한 문장("…한국어 학습자들이…")으로 폴백한다.
   - 같은 문안을 `/desk` 피드 상단 헤더 블록에도 동일하게 사용한다(§4.1).
   - 로그인 폼 아래에는 작은 캡션으로 `읽기에는 로그인이 필요하지 않습니다 · No login needed to read` 를 유지한다.

3. **가입은 초대코드가 있어야만 가능하다.** 모달 하단 `초대코드로 시작하기 / Start with an invite code`.
4. **회원가입 링크를 별도로 두지 않는다.** "가입" 개념 자체가 초대 리딤 플로우 안에만 존재한다.

### 3.3 왜 이 방식인가

| 대안 | 문제 |
|---|---|
| 10명일 때만 로그인 버튼 노출 | 로그인 전에는 누가 접속했는지 알 수 없으므로 기술적으로 불가능(IP/기기 화이트리스트는 해외 모바일 환경에서 비현실적). 구현하더라도 첫 로그인 경로가 사라진다. |
| 숨김 URL (`/desk/xk92m/login`) | 현재 운영자 페이지와 같은 패턴이라 일관성은 있으나, ① 학습자가 URL을 분실할 위험, ② 2년 차·3년 차 인수인계 시 관리 비용, ③ "비밀 공간"이라는 인상이 오히려 폐쇄적. |
| 누구나 가입 + 승인제 | 방문자가 가입했다가 거절당하는 경험이 발생 → 3.1의 우려가 **실제로** 현실화되는 유일한 안. 스팸 가입 관리 부담도 큼. |

**채택안의 장점**

- **배제 없는 투명성**: 방문자는 "막혔다"가 아니라 "이 코너의 저자는 10명"이라는 정보를 얻는다. 저널·전시 도록의 편집 구조와 같은 인식이 형성된다.
- **사업 취지 전달**: 로그인 모달 자체가 사업 소개 지면으로 기능한다. 방문자 5,000명 목표(홍보계획 나)에 기여.
- **지속 가능성**: 사업 종료 후에도 계정·로그인 경로가 그대로 살아 있다. 나르샤 팀이 초대코드 발급을 중단해도 기존 10인의 운영은 무중단. 차년도 참여자에게는 코드만 새로 발급하면 된다.
- **개발 비용**: Supabase Auth 표준 기능 + 초대코드 테이블 1개 + Edge Function 1개.

### 3.4 사후 운영 시나리오 (사업 종료 후)

- 계정과 발행 글은 그대로 유지, 로그인·작성 기능 계속 동작
- 나르샤 팀은 초대코드 발급만 중단 → 신규 저자 유입 자동 차단
- 저자가 이탈을 원하면 `프로필 → 계정 비활성화` (글은 유지 / 전체 삭제 선택 가능)
- 운영비: Supabase Free tier(DB 500MB, Storage 1GB) 내 운영 가능하도록 §6.3 쿼터 정책 적용. 초과 시 Pro tier $25/월.

### 4.1 `/desk` 피드 화면 구성

1. **헤더 블록** — §3.2의 확정 소개 문안(한/영), 참여 저자 아바타 리스트(클릭 시 개인 책상 이동). 크리에이터 파트너에게는 아바타 옆 `파트너 / Partner` 배지 표시

### 4.2 디자인 원칙 — *기존 사이트 그대로*

「나의 한국어 책상」은 **별도의 비주얼 아이덴티티를 만들지 않는다.** 기존 NARSHA 플랫폼과 완전히 동일한 디자인 언어를 사용한다.

- Figma `Narsha MVP ver2` 및 현재 배포본의 색상·타이포·간격·라운드·그림자 토큰을 그대로 사용
- `src/app/components/ui/*` (shadcn/Radix) 기존 컴포넌트를 우선 재사용하고, 신규 컴포넌트는 기존 스타일 규칙을 따라 작성
- `Root` 레이아웃(헤더·푸터)을 그대로 상속. 「나의 한국어 책상」 전용 헤더나 풀블리드 히어로를 만들지 않는다
- 알림은 기존 `sonner` 토스터, 아이콘은 기존 `lucide-react` 사용
- **예외 영역**: 에디터 툴바와 본문 렌더러만 별도 스타일 스코프(`.desk-editor`, `.desk-prose`)를 갖는다. 본문 안의 인용구·구분선·표는 저자가 고른 스타일이 우선하므로 전역 Tailwind 스타일과 격리한다

## 5. 기능 요구사항 — 인증

### 5.1 기술 선택

**Supabase Auth (Email + Password)** 를 사용한다. 이미 `@supabase/supabase-js` 의존성이 있고 Supabase 프로젝트가 연결되어 있다.

- **Magic Link를 기본으로 쓰지 않는 이유**: 인니·필리핀 환경에서 국제 발신 메일이 스팸함으로 분류되거나 지연되는 사례가 잦고, 글을 쓸 때마다 메일함을 여는 마찰이 크다. 대신 **비밀번호 재설정** 경로로 매직링크를 사용한다.
- 세션은 Supabase의 refresh token 기반 유지(기본 1주 → **60일로 연장**). 저자는 사실상 로그인 상태를 유지한다.

### 5.2 초대코드 리딤 플로우

```
운영자                          학습자
  │ 초대코드 발급                  │
  │ (코드 + 대상 라벨 + 만료일)      │
  ├──── 코드 전달 (이메일/왓츠앱) ──▶│
  │                              │ /desk/join?code=XXXX 접속
  │                              │ ① 코드 유효성 검증 (Edge Function)
  │                              │ ② 이메일 / 비밀번호 입력
  │                              │ ③ 표시 이름 · handle · 국가 · 한 줄 소개
  │                              │ ④ 이용약관 · 저작권 · 개인정보 동의
  │◀─── 코드 소진 · 계정 생성 ──────┤
```

**보안 요구사항**

- `invite_codes` 테이블은 **anon 키로 조회 불가** (RLS `SELECT` 전면 차단). 코드 검증·리딤은 Supabase **Edge Function `redeem-invite`** 에서만 수행한다.
- 코드는 DB에 **해시로 저장**(bcrypt 또는 `pgcrypto`), 원본은 발급 시 1회만 노출.
- Service Role Key는 Edge Function 환경변수로만 주입한다. **클라이언트 번들·레포에 절대 포함하지 않는다.**
- 코드 형식: `NARSHA-XXXX-XXXX` (대문자+숫자, 혼동 문자 `0/O/1/I` 제외)
- 속성: 1회용, 기본 만료 30일, 운영자가 즉시 회수(revoke) 가능
- 리딤 시도 rate limit: IP당 시간당 10회

**발급 단위 (확정)**
**1인 1코드.** 참여자 수만큼 각각 다른 코드를 발급하며, 한 코드는 **한 계정 생성에만** 사용되고 즉시 소진된다. 여러 명이 하나의 코드를 공유할 수 없다. `label` 필드에 대상자를 기록해 어느 코드가 누구에게 갔는지 추적한다.

**코드 전달 방식 (확정)**
공동제작자 선발이 확정되면 **나르샤 팀이 운영자 대시보드에서 직접 생성하여 개별 연락으로 전달**한다. 시스템이 자동으로 초대 메일을 발송하지 않는다.

- 운영자 대시보드에서 코드 생성 → 코드 + 라벨 + 만료일이 화면에 1회 표시 → 운영자가 복사해 개별 전달
- 발급 시 함께 복사할 수 있도록 **가입 안내 문장 템플릿(한/영)** 을 코드와 나란히 제공한다
  > 아래 링크로 접속해 「나의 한국어 책상」 계정을 만들어 주세요.
  > `https://narsha-mvp-ver2.vercel.app/desk/join?code=NARSHA-XXXX-XXXX` (2026-XX-XX 만료)
- 코드는 발급 후 다시 볼 수 없다(해시 저장). 분실 시 기존 코드를 회수하고 재발급한다
- 대시보드에는 코드 목록이 `라벨 / 상태(미사용·사용됨·만료·회수) / 발급일 / 사용자` 로 표시되어 누구에게 갔는지 추적 가능

### 5.5 handle (계정 주소) 규칙

**handle이란**: 개인 책상 페이지의 **URL에 들어가는 영문 아이디**다. 표시 이름과 별개로, 주소창에 노출되는 짧은 식별자를 말한다.

```
handle = rina
  → 개인 책상   https://narsha-mvp-ver2.vercel.app/desk/@rina
  → 글 상세     https://narsha-mvp-ver2.vercel.app/desk/@rina/my-first-korean-notebook
```

표시 이름(`display_name`)을 그대로 URL에 쓰지 않는 이유는 ① 한글·현지 문자가 URL에서 깨지고, ② 이름을 바꾸면 기존 링크가 전부 깨지기 때문이다. handle을 따로 두면 저자가 표시 이름을 바꿔도 링크와 SEO가 유지된다.

**규칙 (확정)**

| 항목 | 내용 |
|---|---|
| 결정 주체 | **저자가 직접 입력** (가입 3단계). 나르샤 팀이 지정하지 않는다 |
| 형식 | 소문자 영문·숫자·하이픈, 3~20자. 시작·끝은 영문/숫자 |
| 중복 | 실시간 중복 확인, 사용 중이면 대안 3개 자동 제안 (`rina2`, `rina-jkt`, `rina-kr`) |
| 기본 제안값 | 저자가 입력한 영문 이름 기반 자동 생성 후 수정 가능 |
| 예약어 | `admin`, `api`, `new`, `write`, `manage`, `settings`, `login`, `join`, `narsha` 등 차단 |
| 변경 | 가입 후 **1회만** 변경 가능(설정 화면). 변경 시 이전 handle은 6개월간 새 주소로 301 리다이렉트 후 해제 |

> 도시 접미사(`rina-jakarta`)를 강제하지 않는다. 사업 종료 후에도 저자 본인의 온라인 정체성으로 계속 쓰이는 주소이므로 본인이 애착을 가질 수 있는 이름을 고르게 하는 편이 지속 운영에 유리하다.

### 5.3 권한 모델

| role | 설명 |
|---|---|
| `author` | 초대코드로 가입한 책상 주인. 본인 글 CRUD. |
| `admin` | 나르샤 팀. 전체 글 숨김, 계정 관리. |

`profiles.is_active = false`인 계정은 로그인은 되지만 작성이 차단되고, 기존 발행 글은 유지된다.

**참여 유형 배지 (확정)**

권한은 동일하되, 프로필에 참여 유형을 표시하는 `participant_type` 필드를 둔다. **기능 차이는 없고 표시만 다르다** — 크리에이터 파트너 2인은 현지 채널을 운영하는 공동 파트너이므로 방문자가 맥락을 이해할 수 있어야 하고, 사후 확산 KPI(파트너 채널별 게시 6건 이상) 추적에도 필요하다.

| 값 | 배지 (한 / 영) | 대상 |
|---|---|---|
| `co_creator` | *(배지 없음)* | 브이로그 공동제작 학습자 |
| `creator_partner` | **파트너 / Partner** | 현지 크리에이터 파트너 (도시당 1명) |

- 배지는 기존 `Badge` 컴포넌트를 그대로 사용(§4.2), 별도 색상 체계를 만들지 않는다
- 노출 위치: `/desk` 저자 아바타 리스트, 개인 책상 프로필 헤더, 글 상세 저자 정보
- 파트너 프로필에는 본인 채널 링크 필드(`channel_url`)를 추가로 제공하고 프로필 헤더에 노출한다

### 5.4 RLS 정책 (요약)

```sql
-- 발행 글은 누구나 읽기
create policy "public read published"
  on desk_posts for select
  using (status = 'published' and is_hidden = false);

-- 본인 글은 상태 무관 읽기
create policy "author read own"
  on desk_posts for select
  using (auth.uid() = author_id);

-- 작성은 활성 author 본인만
create policy "author insert own"
  on desk_posts for insert
  with check (
    auth.uid() = author_id
    and exists (
      select 1 from profiles p
      where p.id = auth.uid() and p.role = 'author' and p.is_active
    )
  );

-- 수정·삭제는 본인만
create policy "author update own"
  on desk_posts for update using (auth.uid() = author_id);
create policy "author delete own"
  on desk_posts for delete using (auth.uid() = author_id);
```

Storage 버킷도 동일 원칙: 읽기 public, 쓰기는 `auth.uid()` 접두 경로(`desk/{user_id}/...`)에만 허용.

### 6.3 삽입 요소 상세

#### 사진
- 다중 선택, 드래그&드롭, 붙여넣기 지원
- 클라이언트 리사이즈: 장변 max **1600px**, WebP 변환, 품질 0.82
- 원본 업로드 상한 **10MB** / 리사이즈 후 저장
- 캡션 입력, 정렬(좌·중·우·전체폭)
- 저장 위치: `desk/{user_id}/images/{uuid}.webp`

#### 동영상 — *확정 정책*
1. **외부 링크 임베드 (권장 경로)**: YouTube, Instagram, TikTok, Vimeo URL 붙여넣기 → 자동 임베드 카드 변환. 사업 유튜브 채널·본인 SNS 동시 발행(홍보계획 다)과 자연스럽게 연결된다.
2. **직접 업로드 (보조)**: **60초 이내 / 50MB 이하 / mp4·mov** 만 허용. 편집 없이 찍은 짧은 학습 클립을 위한 경로.
3. **계정당 스토리지 쿼터 500MB.** 80% 도달 시 경고 배너, 100% 도달 시 업로드 차단 + 외부 링크 안내. 10인 × 500MB = 5GB 상한이 예측 가능한 비용 구조를 만든다.

#### 링크
- URL 입력 → 인라인 링크 또는 **카드형 미리보기** 선택
- 카드형은 Edge Function으로 OG 메타 추출 (실패 시 인라인 폴백)
- 모든 외부 링크 `rel="noopener noreferrer nofollow"`, `target="_blank"`

#### 파일
- 허용: pdf, docx, pptx, xlsx, hwp, txt, zip, png, jpg
- 상한 20MB, 계정 쿼터에 합산
- 본문에 파일명·확장자·용량이 표시된 다운로드 카드로 삽입
- 실행 파일·스크립트 확장자는 서버 측 화이트리스트로 차단

#### 일정 (날짜 선택)
- 이미 설치된 `react-day-picker`로 날짜/기간 선택
- 삽입 결과: 날짜 카드 노드 `{ date, endDate?, label }`
- 예: `2026.08.14 (목) · 오늘의 한국어 공부` — 학습 기록 성격상 사용 빈도가 높으므로 툴바 1열에 배치

#### 표
- `@tiptap/extension-table`
- 행·열 삽입/삭제, 셀 병합·분할, 헤더 행 토글, 열 너비 드래그
- 모바일에서는 가로 스크롤 컨테이너로 렌더

#### 장소 (지도)
- **Leaflet + OpenStreetMap 타일 + Nominatim 지오코딩**을 사용한다.
  - *근거*: Google Maps Platform은 결제수단 등록이 필수이고 쿼터 초과 시 과금이 발생 → **사업 종료 후 자생적 운영**이라는 요건과 충돌. 카카오/네이버 지도는 해외 지역 데이터 품질이 낮아 자카르타·마닐라에 부적합. Leaflet+OSM은 무료이며 두 도시 커버리지가 충분하다.
  - Nominatim 이용약관 준수(초당 1회 제한, User-Agent 명시). 사용량 증가 시 자체 프록시 캐시.
- 삽입 플로우: 장소 검색 → 결과 선택 → 지도 미리보기 → 삽입
- 저장 데이터: `{ lat, lng, zoom, label, address }` (지도 이미지가 아닌 좌표를 저장 → 영구 보존)
- 활용 예: "오늘 공부한 카페", "한국문화원", "촬영 장소"

#### 문자표
- 자체 팔레트 (외부 라이브러리 불필요)
- 카테고리: 한글 자모 / 문장부호 / 화살표 / 수학·단위 / 괄호·괘선 / 원문자·번호
- 최근 사용 12개 상단 고정 (localStorage)

#### 각주·주석
- 인라인 각주 마크 → 본문에 위첨자 번호 삽입, 글 하단에 자동 각주 목록 생성

| `draft` | 임시저장. 본인만 열람. |
| `published` | 발행. `/desk` 피드와 개인 책상에 노출. |
| `hidden` | 저자 또는 운영자가 비공개 전환. URL 직접 접근도 차단. |

**자동 임시저장**
- 입력 후 **3초 debounce → localStorage** (네트워크 무관, 브라우저 크래시 복구)
- **60초마다 또는 유의미한 변경 시 서버 `draft` upsert**
- 상단 바에 네이버와 같은 `임시저장 N` 카운터 표시, 클릭 시 저장 목록 → 복원
- 서버 저장본은 최대 20개까지 보관(초과 시 오래된 것부터 삭제)
- 편집 화면 이탈 시 미저장 변경 경고

**발행 전 체크리스트 모달** — 사업계획서의 저작권 검수 요건 반영
- [ ] 대표 이미지 선택 (미선택 시 첫 이미지 자동)
- [ ] 태그 (최대 5개, 자동완성)
- [ ] 요약 1~2문장 (미입력 시 본문 앞 120자 자동)
- [ ] 공개 범위: 전체 공개 / 비공개
- [ ] **저작권 확인**: "이 글에 사용한 사진·영상·음원은 직접 촬영했거나 사용 허락을 받았습니다." (필수 체크)

발행 시 `slug` 생성(제목 슬러그화 + 짧은 해시), `published_at` 기록, 발행 후에도 수정 가능(`updated_at` 표시).

### 6.8 콘텐츠 저장 포맷

```
content_json  jsonb   -- Tiptap JSON. 원본(source of truth)
content_html  text    -- 발행 시 렌더·SEO용 캐시. DOMPurify 위생 처리 후 저장
content_text  text    -- 검색·발췌용 평문
```

Tiptap JSON을 원본으로 두면 향후 다국어 렌더링, 백서 자동 인용, 브이로그 자막 연동 시 구조를 재활용할 수 있다.

## 8. 다국어

**한국어 + 영어 2개 언어**를 지원한다.

- 인터페이스 문자열은 `src/i18n/{ko,en}.json`으로 분리, 간단한 컨텍스트 기반 훅으로 전환 (i18next 도입은 과함)
- 헤더에 `KO / EN` 토글, 선택값 localStorage 저장
- **글 본문은 저자가 쓴 언어 그대로 저장·표시**한다. 자동 번역하지 않는다 — "학습자 본인의 언어로 기록·공유"라는 사업 추진목적에 부합
- 글 작성 시 `lang` 태그(ko/en/id/tl) 선택 → 피드 필터에 사용
- 에디터 UI·오류 메시지·온보딩 가이드는 **영문 검수 필수** (Author 다수가 영어 사용자)

## 9. 접근성 · 성능 · 보안

**성능**
- 에디터 번들은 `React.lazy`로 코드 분할 — 방문자에게 로드되지 않게 한다
- 이미지 `loading="lazy"`, 반응형 `srcset`
- 지도·유튜브 임베드는 **클릭 후 로드**(façade 패턴)
- 목표: `/desk` 피드 LCP < 2.5s (3G Fast 기준)

**보안**
- `content_html` 저장·렌더 시 **DOMPurify** 위생 처리 (XSS 차단)
- 업로드 파일: 확장자 화이트리스트 + MIME 검증 + 크기 제한
- 모든 시크릿(Supabase Service Role Key, 관리자 비밀번호)은 **환경변수 / Vercel Environment Variables** 로만 주입. 레포·클라이언트 번들에 하드코딩 금지
- 초대코드 리딤 rate limit (IP당 시간당 10회)
- Supabase RLS를 모든 신규 테이블에 `enable row level security` 적용

**개인정보**
- 수집 항목: 이메일, 표시 이름(가명 허용), 국가, 프로필 이미지 — **실명·생년월일·연락처는 수집하지 않는다**
- 공개 노출: 표시 이름, 국가, 소개, 아바타만. 이메일 비공개
- 기존 `/privacy`, `/terms` 문서에 「나의 한국어 책상」 조항 추가 필요
- 계정 삭제 요청 시 30일 내 처리, 글 보존 여부는 저자가 선택

## 12. 온보딩 가이드

**개별 전달용 PDF 1종만 만든다. 사이트에는 어떤 형태로도 넣지 않는다.**

- `/desk/help` 도움말 페이지 — **만들지 않음**
- 사이트 내 PDF 다운로드 링크 — **만들지 않음**

에디터 기능이 별도 매뉴얼을 상시 비치할 만큼 복잡하지 않고, 방문자용 코너 설명은 이미 `/desk` 헤더 블록(§4.1)이 담당한다. 툴바 아이콘 툴팁과 에디터 플레이스홀더(§9 접근성 요건)로 화면 안의 기본 힌트는 충분히 제공된다.

**제작 순서: 기능 구현 → PDF.** 실제로 배포된 화면을 스크린샷으로 담아 만든다. 구현하지 못한 기능은 PDF에서 **그냥 뺀다.** 문서를 먼저 쓰고 기능을 맞추지 않는다.

### 12.1 저자용 시작 가이드 (PDF)

초대코드와 함께 나르샤 팀이 개별 연락으로 전달하는 문서. 배포되지 않고 사이트에도 올리지 않는다.

- 형식: PDF, A4 8~10쪽, **영문 기본 / 한국어 병기**
- 목차
  1. 「나의 한국어 책상」이란 — 사업 소개, 내 글이 어디에 어떻게 보이는지
  2. 계정 만들기 — 초대코드 입력부터 handle 정하기까지 (스크린샷)
  3. 첫 글 쓰기 — 사진 넣기, 인용구·구분선, 임시저장, 발행 (스크린샷)
  4. 좋은 기록을 위한 팁 — B형(기록형) 스크립트와 연결되는 기록 예시
  5. **꼭 지켜주세요** — 저작권(직접 찍은 사진·영상, 음원 주의), 타인 촬영 시 동의, 개인정보 노출 주의
  6. 문제가 생기면 — 나르샤 팀 연락처, 비밀번호 재설정 방법
- 제작 시점: **8/7까지 완성** → 8/10 오픈과 함께 코드·가이드 동시 전달
- 8월 2차 기획회의(3자 화상회의)에서 15분 시연으로 보완

### 12.2 개정 관리

Phase 2 기능(표·지도·각주 등)이 배포되면 PDF에 해당 장을 추가해 **개정판을 다시 개별 전달**한다. 파일 첫 장에 개정일을 표기한다. 전달 대상이 소수(최대 10인)이므로 개별 재전달 부담은 크지 않다.

> 나르샤 팀이 법무 검토를 받을 때 **출발점으로 쓰기 위한 실무 초안**이며, 그대로 시행해서는 안 됩니다. 국고보조사업의 결과물 귀속, 해외 거주자 대상 약관의 준거법, 인도네시아·필리핀 개인정보보호법 적용 여부는 반드시 **변호사 등 전문가의 검토를 받으시기 바랍니다.** 특히 §B.4의 확인 쟁점을 그대로 들고 가시면 상담이 빨라집니다.

### B.1 기존 `/terms`에 신설할 장(章)

기존 이용약관에 **「제○장 나의 한국어 책상」** 을 신설하고 아래 조문을 넣는 방식을 제안한다. 기존 조항(앱 리뷰, 학습 유형 검사)은 손대지 않는다.

---

**제○조 (정의)**

1. "책상 주인"이란 나르샤 팀이 발급한 초대코드로 계정을 생성하여 「나의 한국어 책상」에 게시물을 작성할 수 있는 이용자를 말합니다.
2. "게시물"이란 책상 주인이 「나의 한국어 책상」에 작성·업로드한 글, 사진, 영상, 파일, 댓글 및 프로필 정보 일체를 말합니다.
3. "본 사업"이란 2026 국민공공외교 사업 「세계의 한국어 책상」을 말합니다.

**제○조 (계정)**

1. 계정은 나르샤 팀이 발급한 초대코드를 통해서만 생성할 수 있습니다.
2. 책상 주인은 계정 정보를 제3자와 공유해서는 안 되며, 계정을 통해 발생한 활동에 책임을 집니다.
3. 책상 주인은 언제든지 계정의 비활성화 또는 삭제를 요청할 수 있습니다. 이 경우 게시물의 처리 방식(전부 유지 / 전부 삭제 / 익명 전환)을 함께 선택할 수 있으며, 나르샤 팀은 요청일로부터 30일 이내에 처리합니다.
4. 나르샤 팀은 제○조(금지행위)를 중대하게 위반한 계정에 대하여, 사전 통지 후 작성 권한을 정지할 수 있습니다. 다만 이미 발행된 게시물의 저작권 귀속은 영향을 받지 않습니다.

**제○조 (게시물의 저작권 귀속)**

1. **게시물의 저작권은 이를 작성한 책상 주인에게 귀속됩니다.** 나르샤 팀은 게시물에 대한 저작권을 양도받지 않습니다.
2. 책상 주인은 자신의 게시물을 본인의 SNS, 블로그, 포트폴리오 등 다른 매체에 자유롭게 게시·활용할 수 있습니다.

**제○조 (이용허락의 범위)**

1. 책상 주인은 게시물을 발행함으로써, 나르샤 팀에 대하여 아래 각 호의 목적 범위에서 게시물을 이용할 수 있는 **무상의, 비독점적, 양도 불가능한 이용권**을 부여합니다.
   1. 「나의 한국어 책상」 및 NARSHA 플랫폼에서의 게시·저장·전송·검색 노출
   2. 본 사업의 홍보를 위한 사용 (플랫폼 소개, SNS 게시, 보도자료, 발표 자료)
   3. 본 사업의 산출물인 「글로벌 한국어 학습 백서」 및 결산 보고 자료에의 인용
   4. 본 사업의 브이로그·숏폼 콘텐츠 제작 시의 활용
   5. 사업 수행 기관에 대한 사업 결과 보고
2. 제1항의 이용권은 **본 사업의 목적 범위 내에서만** 행사되며, 나르샤 팀은 게시물을 제3자에게 판매하거나 상업적으로 재사용하지 않습니다.
3. 나르샤 팀은 게시물을 이용할 때 **작성자의 표시 이름을 함께 표기**합니다. 다만 백서 등에서 학습자 보호를 위해 가명 처리가 필요한 경우, 사전에 책상 주인의 동의를 받습니다.
4. 나르샤 팀은 게시물의 본질적 내용을 변경하지 않는 범위에서, 화면 표시·자막·요약 등을 위한 **형식적 편집**을 할 수 있습니다.
5. 제1항의 이용권은 **본 사업 종료 후에도 존속**합니다. 다만 책상 주인이 게시물을 삭제한 경우, 나르샤 팀은 삭제 시점 이후의 신규 이용을 중단합니다. 이미 인쇄·배포되었거나 제3자 플랫폼에 게시된 자료에 대해서는 회수가 불가능할 수 있습니다.

**제○조 (제3자의 권리 및 초상권)**

1. 책상 주인은 게시물이 제3자의 저작권, 초상권, 상표권, 명예 및 그 밖의 권리를 침해하지 않음을 보증합니다.
2. 책상 주인은 다음 사항을 준수해야 합니다.
   1. 사진·영상은 **직접 촬영**했거나 사용 허락을 받은 것이어야 합니다.
   2. 배경음악은 저작권이 소멸했거나 CC·로열티프리 음원이어야 합니다.
   3. **타인이 식별 가능한 형태로 등장하는 경우, 사전에 촬영·공개 동의를 받아야 합니다.**
   4. 교재·앱 화면 등을 인용할 때에는 출처를 표기하고, 정당한 인용의 범위를 넘지 않아야 합니다.
3. 제3자로부터 권리 침해 주장이 제기된 경우, 나르샤 팀은 해당 게시물을 임시로 비공개 처리하고 책상 주인에게 통지합니다.

**제○조 (금지행위)**

책상 주인은 다음 행위를 해서는 안 됩니다.

1. 타인의 개인정보(실명, 연락처, 주소, 학교·직장 정보 등)를 동의 없이 게시하는 행위
2. 특정 개인·집단·국가에 대한 혐오, 차별, 비방을 담은 게시
3. 허위 사실의 게시
4. 광고·홍보를 주된 목적으로 하는 게시
5. 본 사업의 목적과 무관한 정치적·종교적 선전
6. 법령을 위반하는 게시

**제○조 (게시물의 관리)**

1. 책상 주인은 자신의 게시물을 언제든지 수정, 비공개 전환, 삭제할 수 있습니다.
2. 나르샤 팀은 게시물이 제○조(제3자의 권리)·제○조(금지행위)를 위반하는 것으로 판단되는 경우, 해당 게시물을 비공개 처리할 수 있습니다. 이 경우 지체 없이 그 사유를 책상 주인에게 통지하고, 책상 주인은 이의를 제기할 수 있습니다.
3. 나르샤 팀은 게시물의 내용을 사전에 검열하지 않습니다.

**제○조 (서비스의 지속 및 종료)**

1. 나르샤 팀은 본 사업 종료 후에도 「나의 한국어 책상」의 열람 및 작성 기능을 지속적으로 제공하기 위해 노력합니다.
2. 부득이한 사유로 서비스를 종료하는 경우, 나르샤 팀은 **최소 90일 전에 공지**하고, 책상 주인이 자신의 게시물 전체를 내려받을 수 있는 방법을 제공합니다.

**제○조 (준거법 및 분쟁 해결)**

1. 본 약관은 대한민국 법률에 따라 해석됩니다.
2. 분쟁이 발생한 경우 당사자는 우선 협의를 통해 해결하며, 협의가 이루어지지 않을 경우 관할 법원에 소를 제기할 수 있습니다.

### B.4 법무 검토 시 확인해야 할 쟁점

상담 시 아래를 그대로 질문하면 된다.

1. **국고보조사업 결과물의 귀속** — 본 사업 협약서·공모 지침에 산출물의 권리 귀속이나 주관기관의 사용권을 규정한 조항이 있는지, 있다면 위 약관과 충돌하지 않는지. **가장 먼저 확인해야 할 항목.**
2. **해외 거주자 대상 약관의 준거법·관할** — 인도네시아·필리핀 거주자를 대상으로 대한민국 법을 준거법으로 지정하는 것이 유효한지, 소비자 보호 규정상 제한이 있는지.
3. **해외 이용자의 개인정보** — 인도네시아 개인정보보호법(UU PDP), 필리핀 Data Privacy Act 2012의 적용 여부 및 추가 고지 의무.
4. **개인정보 국외 이전** — Supabase·Vercel 서버 소재국 기준 위탁·국외이전 고지가 충분한지.
5. **이용허락의 존속** — 사업 종료 후 및 계정 삭제 후에도 백서·영상에 이미 반영된 콘텐츠를 계속 사용할 수 있는지, 그 범위를 어떻게 특정해야 하는지.
6. **크리에이터 파트너와의 관계** — 별도 업무 협의서(MOU)의 콘텐츠 조항과 본 약관이 중복·충돌하지 않는지.
7. **초상권** — 학습자가 촬영한 영상에 등장하는 제3자(가족·친구·현지 커뮤니티)의 동의를 서면으로 받아야 하는지, 받는다면 양식이 필요한지.
8. **미성년자** — 참여 자격이 만 18세 이상이나, 게시물에 미성년자가 등장할 경우의 추가 요건.
